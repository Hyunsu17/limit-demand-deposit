# 테스트 코드 작성 정리

한도요구불(입출금통장) 프로젝트 · 2026-06 ~ 2026-08 · 작성일 2026-09-01

프로젝트는 여기서 중단한다. 진행하면서 가장 많이 다룬 것이 테스트 코드였고,
무엇을 어떤 이유로 그렇게 작성했는지를 정리한다.

## 규모

| 항목 | 값 |
|------|-----|
| 테스트 파일 | 21개 |
| 테스트 코드 | 약 2,200줄 |
| 전체 통과 | 83개 (1개 보류) |
| 기간 | 약 2개월 |

---

## 1. 테스트를 4단계로 나눴다

처음에는 단위 테스트와 통합 테스트 두 가지로 생각했다.
작성하다 보니 성격이 다른 4가지로 갈라졌다.

| 단계 | 확인 대상 | DB | 파일 수 |
|------|----------|-----|--------|
| ① 규칙 테스트 | 계산과 상태변경 규칙 | 사용 안 함 | 5개 |
| ② 흐름 테스트 | 단계 간 호출 순서와 중단 여부 | 사용 안 함 (가짜 부품) | 5개 |
| ③ DB 테스트 | DB 제약이 실제로 막는지 | 진짜 DB | 7개 |
| ④ 전체 테스트 | API 호출부터 DB 저장까지 | 진짜 DB | 3개 |

---

## 2. ① 규칙 테스트 — 계산 검증

DB나 서버 없이 자바 객체만 만들어서 확인한다. 가장 빠르고 가장 많이 작성했다.

대표적인 것이 입금 가능 금액 계산이다.
규칙 자체는 한 줄이다. `MIN(통장에 더 담을 수 있는 금액, 이번 달에 더 넣을 수 있는 금액)`

이 한 줄을 7개 경우로 나눴다.

| 경우 | 확인 이유 |
|------|-----------|
| 왼쪽이 작을 때 | 기본 동작 |
| 오른쪽이 작을 때 | 반대 방향 |
| 둘이 같을 때 | 경계 |
| 여유가 0일 때 | 경계 |
| 여유가 음수일 때 | 한도를 낮추면 실제로 발생. 0으로 막아야 함 |
| 첫 입금일 때 | 잔액 0, 누적 0 |
| 소수점 자릿수가 다를 때 | DB에서 조회하면 `5000`이 `5000.0000`으로 옴 |

계산식이 한 줄이어도 테스트는 한 줄이 아니다. 틀리는 지점은 평범한 값이 아니라
0, 음수, 자릿수 같은 끝값이었다.

---

## 3. ② 흐름 테스트 — 순서와 중단 확인

계좌 개설은 여러 단계를 거친다.
`신청 저장 → 외부 기관(NCIS)에 1인1계좌 조회 → 계좌 확정 → 실패 시 되돌리기`

여기서 진짜 DB나 진짜 외부 기관을 호출하면 테스트가 느리고 불안정하다.
그래서 가짜 부품(Mockito)을 끼워 넣는다. NCIS가 거절로 응답하는 상황 같은 것을 한 줄로 만들 수 있다.

이 단계에서 중요했던 것은 호출 순서보다 호출하지 않았는지 여부였다.

```java
// 첫 단계(신청 저장)가 실패하도록 만들고
when(applyService.apply(request)).thenThrow(new BusinessException(ErrorCode.UNDER_AGE));

// 외부 기관을 한 번도 호출하지 않았는지 확인한다
verify(ncisClient, never()).check(any());
```

앞 단계가 실패했는데 뒤 단계가 실행되면 미성년자 신청에 외부 조회 비용이 나가고
불필요한 데이터가 남는다. 실패했을 때 뒤로 진행되지 않는지를 확인하는 것이 이 단계의 목적이다.

---

## 4. ③ DB 테스트 — 실제 PostgreSQL 사용

### 메모리 DB(H2)를 쓰지 않은 이유

메모리 DB를 쓰면 빠르다. 그런데 확인하려는 대상이 DB마다 동작이 다른 것들이었다.

- 한 사람이 계좌를 두 개 만들지 못하게 막는 제약
- 실패 기록에 사유가 없으면 저장을 거부하는 제약
- 같은 계좌를 동시에 변경할 때 순서를 강제하는 잠금

메모리 DB에서 통과해도 실제 운영에서 통과한다는 보장이 없다.
그래서 테스트 실행 시 도커로 실제 PostgreSQL을 띄우는 방식(Testcontainers)을 사용했다.

설정은 다음과 같다.

```yaml
url: jdbc:tc:postgresql:16:///limitdeposit   # tc = 실행 시 컨테이너 자동 기동
```

### 이 단계에서 제외한 테스트

`save()`를 호출하면 저장되는지 같은 프레임워크 동작은 테스트하지 않았다.
대신 DB가 실제로 거부하는지, 제약 조건이 걸리는지를 확인했다.

무엇을 작성할지보다 무엇을 작성하지 않을지를 정하는 편이 어려웠다.
기준은 실패했을 때 그것이 내 코드의 문제인지 프레임워크의 문제인지였다.

## 5. ④ 전체 테스트 — API에서 DB까지

가짜 부품을 쓰지 않는다. 실제 서버를 띄우고 HTTP 요청을 보낸 다음
SQL로 DB를 직접 조회해서 확인한다.

입금 성공 케이스에서 확인한 항목은 4가지다.

1. 응답이 200이고 응답 본문의 잔액이 맞는가
2. 통장 잔액이 입금액만큼 증가했는가
3. 요청 원본 기록이 `완료`로 바뀌고 실패사유가 비어 있는가
4. 거래내역의 잔액이 통장 잔액과 일치하는가

4번이 핵심이다. `통장 잔액 = 거래내역 합계`가 어긋나면 원장 정합성이 깨진 것이다.

### 테스트에 `@Transactional`을 붙이지 않았다

보통은 붙인다. 테스트가 끝나면 저장한 데이터가 자동으로 지워져서 편하다.
그런데 붙이면 테스트 안의 모든 작업이 하나로 묶인다.

확인하려던 것은 그 반대였다. 입금이 한도 초과로 거절될 때
거절 기록은 남고 잔액은 바뀌지 않아야 한다. 즉 일부는 저장되고 일부는 취소돼야 한다.
자동 정리를 켜면 전부 한 덩어리가 되어 이 구분이 사라진다.

그래서 자동 정리를 포기하고 테스트 시작마다 `DELETE`로 직접 정리했다.
대신 실제로 데이터가 남기 때문에 처리해야 할 것이 두 가지 생겼다.

- 뒷정리를 하지 않으면 다음 테스트 클래스가 영향을 받는다. 종료 시에도 삭제하도록 했다.
- 다른 테스트와 고객번호가 겹치면 충돌한다. `8888`처럼 겹치지 않는 값을 사용했다.

테스트의 기본 설정이 검증 대상 자체를 지울 수 있다는 것을 여기서 확인했다.

## 6. 동시성 테스트 — 스레드 2개

두 요청이 같은 계좌에 동시에 입금하면 잔액이 어긋날 수 있다.
막는 장치(비관적 잠금)는 걸어뒀지만 실제로 막히는지는 확인한 적이 없었다.

앞의 방식으로는 확인할 수 없다. 이유가 세 가지다.

| 문제 | 내용 |
|------|------|
| 작업 묶음이 하나뿐 | 같은 묶음 안에서 두 번 잠그는 것은 자기 자신이라 막히지 않음 |
| 묶음이 스레드에 종속 | 한 스레드에서 독립적인 묶음 2개를 만들 수 없음 |
| 데이터가 저장 전 상태 | 상대 스레드에서 계좌가 보이지 않음. 막히는 것이 아니라 없는 상태 |

그래서 스레드 2개를 띄우고 신호(CountDownLatch) 2개로 순서를 맞췄다.

```
T1: 계좌를 잠근다 → 잠갔다는 신호 → T2가 끝날 때까지 대기
T2: 신호를 받고 출발 → 같은 계좌를 잠그려다 실패해야 정상
```

문제가 하나 더 있었다. 잠금에 실패하면 무한정 대기해서 테스트가 끝나지 않는다.
그래서 이 테스트에서만 0.5초 안에 잠그지 못하면 실패하도록 설정했다.
운영 코드는 수정하지 않았다. 테스트를 위해 실제 동작을 바꾸면 검증의 의미가 없어진다.

### 잠금 설정을 제거하고 다시 실행했다

테스트가 통과해도 그것이 실제로 잠금을 검증하는지는 알 수 없다.
그래서 잠금 설정을 제거하고 다시 실행했다. 테스트가 실패했다.
통과하는 것보다 제거했을 때 실패하는지가 판단 기준이었다.

## 7. 테스트로 확인한 잘못 알고 있던 것 3가지

| 알고 있던 것 | 실제 |
|-------------|------|
| 잠금이 `FOR UPDATE`로 실행된다 (주석에 기재) | `FOR NO KEY UPDATE`로 실행됐다. 프레임워크가 그렇게 생성한다 |
| 실패 시 A 오류가 발생한다 | B 오류가 발생했다. 타입이 달랐다 |
| 저장 시점에 오류 종류가 바뀔 것을 우려했다 | 바뀌지 않았다. 대비 코드가 불필요했다 |

세 가지 모두 문서와 주석에 확정적으로 적어둔 내용이었다.

## 8. 사용한 도구

| 도구 | 용도 |
|------|------|
| JUnit 5 | 테스트 실행 기본 틀 |
| Mockito | 가짜 부품 주입. 응답 지정과 호출 여부 확인 |
| AssertJ | 결과 비교. `assertThat(x).isEqualTo(y)` 형태 |
| Testcontainers | 테스트 실행 시 PostgreSQL을 도커로 자동 기동 |
| WireMock | 외부 기관(NCIS) API를 대신하는 가짜 서버 |
| MockMvc | 서버를 띄우지 않고 HTTP 요청을 넣는 도구 |
| Flyway | 테스트 DB에도 실제와 동일한 테이블 생성 |

### 가짜 서버 기동 시점

가짜 서버는 비어 있는 포트를 실행 시점에 잡는다. 그 포트 번호를 앱 설정에 전달해야 하는데,
일반적으로 쓰는 시작 지점(`@BeforeAll`)이 앱 설정을 읽는 시점보다 늦을 수 있다.
클래스가 로딩되는 시점에 바로 기동하도록 변경했다.

## 9. 금액을 다루면서 정한 규칙

### 금액 비교에 `isEqualTo`를 쓰지 않는다

`1000`과 `1000.0000`은 값은 같지만 자바에서는 다른 것으로 판정된다.
DB에서 조회하면 자릿수가 붙어서 나오기 때문에 이걸 모르면 정상 동작인데도 테스트가 실패한다.

```java
assertThat(balance).isEqualTo("1000");             // 자릿수가 다르면 실패
assertThat(balance).isEqualByComparingTo("1000");  // 값으로만 비교
```

자릿수가 달라도 같은 금액으로 판단하는지를 별도 테스트 케이스로 만들어뒀다.

### 이름 규칙

```java
@DisplayName("월입금한도를_초과하면_거절되고_원장은_그대로_원본만_FAILED로_남는다")
void deposit_exceedsMonthlyLimit_rejected_ledgerUnchanged_rawMarkedFailed() {
    // given  — 상황 준비
    // when   — 실행
    // then   — 확인
}
```

`대상 _ 조건 _ 기대결과` 순서로 통일했다.
테스트가 실패했을 때 코드를 열지 않고 이름만으로 무엇이 깨졌는지 알 수 있게 하기 위해서다.

## 10. 하지 못한 것

| 항목 | 상태 |
|------|------|
| 전역 오류 처리기 테스트 | 없음 |
| 동시 입금 시 잔액 합계 검증 | 미작성. 설계만 있음 |
| 다른 계좌는 막히지 않는지 (잠금 범위) | 미작성 |
| 부하 테스트 | 범위에서 제외 |

## 정리

- 테스트는 계산, 흐름, DB, 전체 4단계로 갈렸고 각 단계가 확인하는 대상이 다르다.
- 기본 설정을 그대로 쓰면 안 되는 경우가 있다. 자동 정리 옵션 하나가 검증 대상을 지웠다.
- 통과 여부보다 설정을 제거했을 때 실패하는지가 테스트를 신뢰할 수 있는 기준이었다.
- 문서와 주석에 확정적으로 적어둔 내용 3가지가 틀렸고, 그것을 확인한 수단이 테스트였다.
